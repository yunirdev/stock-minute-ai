# 项目迁移主计划

状态：执行路线图（2026-07-26）  
目标：在不牺牲现有 Paper 交易安全边界的前提下，逐步迁移到“统一多源研究、自动执行、版本化持仓运营”的产品模型。  
相关定义：[产品运行模型](PRODUCT_OPERATING_MODEL.md)、[目标架构](TARGET_ARCHITECTURE.md)、[ADR 0001](decisions/0001-autonomous-multidimensional-trading-model.md)。

## 总原则

- **并行运行、逐段切换**：新状态先以只读/影子方式生成和审计，验收后才成为 Runtime 的强制输入；不要一次重写 Runtime。
- **不扩张权限**：全程仅 Alpaca Paper；Runtime 仍是唯一订单提交者；订单仍为限价单。没有逐笔人工审批，但既有确定性风险、Kill Switch、幂等性、持久化和对账不得移除。
- **数据先于 Agent**：先把来源、时间、质量与降级明确下来，再让 TradingAgents 消费统一输入。LLM 只能提供证据，不能变成执行通道。
- **持仓连续性优先**：任何新计划生命周期功能先保护已成交仓位；每日研究不会直接覆盖已持仓的计划。
- **一次只改变一个生产边界**：每个任务采用“范围 / 不做 / 验收 / 回滚”格式，完成相关测试与全量 `pytest` 后才进入下一任务。

## 阶段总览

| 阶段 | 交付物 | 是否改变自动下单 | 完成判定 |
| --- | --- | --- | --- |
| 0. 基线冻结与缺口修复 | 可重复的安全基线、关键执行缺口修复 | 可改变，但只修正拒绝/错误行为 | Paper 沙箱回归全部通过 |
| 1. 研究快照基础 | `ResearchSnapshot` 与来源清单 | 否，影子记录 | 当前路径与快照可逐字段对照 |
| 2. 数据中心迁移 | 统一 Data Hub 与质量/降级规则 | 否，双读比较 | 主/备数据差异可解释且可审计 |
| 3. TradingAgents 适配 | 快照驱动的每日深度研究 | 否，先影子 | 每日研究可重放、可溯源 |
| 4. 持仓计划生命周期 | `PositionPlan`、失效事件、恢复 | 是，受控接入 | 重启、部分成交、调整均可恢复 |
| 5. 执行路径收口 | 最终计划状态机与风险/分配收口 | 是 | 没有旁路下单或方向/上限错误 |
| 6. 全市场筛选扩展 | 可治理的 universe 与关注池 | 否，先只影响研究池 | 成本、覆盖率、质量达到门槛 |
| 7. 运营可观察性 | NiceGUI/Discord 读模型、运行手册 | 否 | 每笔计划和数据来源可追溯 |
| 8. 长期 Paper 验证 | 稳定性、数据质量和策略表现报告 | 否 | 达到事先定义的连续运行门槛 |

阶段按顺序实施；阶段 6 可在阶段 3–5 的非侵入部分并行准备，但不得提前接入自动执行。

## 阶段 0：冻结基线并修复已知执行缺口

**目的**：先证明当前生产路径不会因已知逻辑错误而产生错误方向、超仓或不可控风险；这是后续迁移的地基。

**任务切片**：

1. 修复 `PaperDecision` 的 BUY/SELL 方向到 ATR `TradePlan` 的完整传递；SELL 不得因候选分数变为 BUY。
2. 在分配、风险和订单意图三个边界验证“现有仓位 + 新增仓位”不超过累计仓位上限；重复 tick、部分成交和重启都适用。
3. 在风险引擎实际执行路径强制单笔最大风险比例，拒绝超过配置的止损风险。
4. 完成启动对账：把 broker 仓位、开放订单、成交与本地持久化状态明确匹配；无法解释时 fail-closed，绝不猜测或重复下单。
5. 建立一份可重复的 Paper smoke 场景：BUY、SELL、拒绝、部分成交、网络未知、重启恢复。

**不做**：不改 UI，不扩展数据源，不改 TradingAgents，也不引入人工审批。

**验收**：

- 每项缺口先有失败回归测试，再修复；相关测试、全量 `pytest`、Ruff、compileall 通过。
- 任一拒绝都无 broker 提交；重复运行产生相同 idempotency key；对账异常阻塞新单但保留监控。
- 使用仅 Paper 的隔离账户完成上述 smoke 场景，审计记录完整。

**回滚**：保持数据库向后兼容；新门槛有问题时仅回退到上一版 Paper Runtime，绝不删除订单、成交或审计记录。

## 阶段 1：研究快照基础（影子写入）

**目的**：定义且持久化 `ResearchSnapshot`，不改变任何现有决策输入。

**范围**：schema/migration、source manifest、质量状态、抓取/截止时间、payload 版本、快照 id；将现有 Runtime、每日研究、策略统计使用的输入记录为快照引用。

**验收**：同一交易日、同一 symbol 的研究可以从快照重放；每个关键字段能追溯来源和 `as_of`；某来源失败显示为失败或降级，不能伪装成新鲜数据。

**切换条件**：影子快照连续 10 个交易日覆盖率达标，且与当前实际输入的差异都已分类为预期或缺陷。

## 阶段 2：统一 Data Hub（双读，不切执行）

**目的**：将散落的数据调用收敛为领域适配器和统一质量政策。

**范围**：

- 行情/账户/订单：Alpaca 主源；本地缓存与 Yahoo Finance 只能以明确降级状态出现。
- 披露/财务：SEC EDGAR 主源，补充源受版本和时间边界约束。
- 新闻/事件/日历：Finnhub、Nasdaq、WallStreetCN 等适配器，各自有 TTL、失败策略和来源记录。
- 宏观/情绪/预期：FRED、StockTwits、Reddit、Polymarket 作为研究维度，不可直接成为订单指令。

**验收**：双读期间 Data Hub 输出与旧路径逐项比较；价格/账户类不允许无解释差异，研究补充类必须保留质量和新鲜度；每个 API 有超时、速率限制、缓存和失效测试。

**切换条件**：连续 20 个交易日没有未分类的关键数据差异，且失败降级演练通过。

## 阶段 3：TradingAgents 快照适配（每日影子研究）

**目的**：让 TradingAgents 成为可重放的每日研究消费者与证据生产者，而不是独立不透明数据管线。

**范围**：传入 `snapshot_id`/manifest，输出研究 run、模型版本、证据和失败原因；保留其必要外部数据适配器，但将结果登记到快照。Runtime 只读取当天冻结且可信的证据。

**验收**：使用同一快照能重现同一研究输入；模型超时、外部源缺失或不可信证据均 fail-closed 或显式量化模式；每日批次不会在 tick 内运行。

**切换条件**：连续 20 个交易日成功生成可审计研究，失败路径不会影响 Runtime 监控或造成绕过。

## 阶段 4：持仓计划生命周期

**目的**：用 `PositionPlan` 取代“每天重新计算就覆盖旧点位”的隐式行为。

**范围**：首次成交创建不可变基线；版本链；`InvalidationEvent` 与 `PositionAdjustment`；止损收紧规则；部分成交与重启恢复；退出/减仓的订单意图关联。

**自动调整边界**：仅接受价格触发、broker 事实、公司行为、交易限制及经过确定性规则验证的策略失效。LLM 文本或普通次日观点不能单独触发调整。

**验收**：

- 次日研究改变观点时，已持仓计划不变且产生解释性比较记录。
- 触发有效失效事件时，自动产生新版本、审计原因和幂等订单意图。
- 重启前后，对同一仓位、开放订单、部分成交和已处理事件不重复操作。

**切换条件**：在 Paper 环境连续 30 个交易日运行，所有持仓均可从数据库和 broker 双向解释。

## 阶段 5：执行路径收口

**目的**：将候选、最终计划、订单意图与持仓调整收敛为一条无旁路的状态机。

**范围**：`CandidatePlan → FinalTradePlan → OrderIntent → PositionPlan/PositionAdjustment`；将策略方向、风险、累计仓位、计划有效期和研究证据在每个转换处校验；旧接口先成为适配层再删除。

**验收**：静态检查证明 Agent/UI 不能导入 broker 或提交订单；BUY/SELL、仓位上限、单笔风险、Kill Switch、幂等与订单恢复都有端到端回归测试；没有 enabled/shadow/手工批准的双路径残留。

## 阶段 6：全市场筛选与关注池扩展

**目的**：在可控成本与数据质量下，扩大可研究标的范围，而不是把所有标的直接送入深度 Agent。

**范围**：universe 版本、可交易/流动性门槛、资产类型覆盖、去重、每日初筛评分、研究预算和重点池容量。

**验收**：每个进入或离开关注池的原因可解释；筛选失败不会清空已有有效持仓计划；研究量、API 配额和每日完成时间不超过预设预算。

## 阶段 7：可观察性与运营

**目的**：让自动化可被理解、排障和审计，而不变成人工下单控制台。

**范围**：NiceGUI 的数据来源、快照质量、研究/计划/持仓版本链、对账和阻塞状态只读展示；Discord 简报模板和发送审计；运行手册、故障分级与数据库备份恢复演练。

**验收**：任一订单可在 UI 中追溯到计划、研究快照、数据源、风险结果和 broker 状态；外部发送保持显式启用；UI 不可改变 broker 交易权限或绕过 Runtime。

## 阶段 8：长期 Paper 验证与发布判定

**目的**：验证系统的运营正确性与研究质量，不能仅凭回测或单日成功认定完成。

**最低门槛**：

- 连续 60 个预定交易日稳定运行，且每天有完整数据质量和研究/执行报告。
- 零未解释重复单、零未经记录的计划改写、零无法解释的 broker/本地状态差异。
- 对数据缺失、API 超时、Runtime 重启、部分成交、市场关闭和 Kill Switch 完成演练。
- 报告 Paper 的成本、滑点、成交率、回撤、策略样本量与风险预算占用；以风险调整后指标评估，不承诺盈利。

“完成”仅表示目标架构在 Paper 环境达到上述稳定性标准；任何实盘授权都是独立产品决策，不属于本迁移计划。

## 执行纪律

每个实际开发任务必须写成如下形式，避免再次进行大范围重复审查：

```text
任务类型：实现 / 审查 / 诊断
范围：<模块边界>
目标：<一个可验证结果>
不做：<明确排除项>
验收：<新增回归测试 + 相关测试 + 全量 pytest>
回滚：<开关、兼容迁移或版本回退方式>
```

阶段结束必须产出：迁移记录、测试结果、数据迁移说明、已知限制和下一阶段的精确任务列表。若验收不通过，修复本阶段，不提前扩展范围。
